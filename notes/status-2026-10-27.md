## What the night established

1. The public fixture reproduces the private app's behaviour at a third of the scale:
   plugin isolate 4.4 to 4.7 s per run as shipped, host alone 0.9 s warm and 4.5 to 6.6 s
   cold, the same double resolution (1,330 `ResolvedUnitResult` events for 665 libraries)
   and the same fine-dependency overhead.
2. Each patch does what its measurement predicted, with all package tests passing and
   `dart analyze` clean on the changed packages (`patches/README.md`): persistent store
   4.4 → 1.55 s warm; fine dependencies off −1 s cold and −0.25 s warm; driver cache −0.3 s
   and half the resolution events; combined **1.1 to 1.2 s warm, 3.7 s first run**.
3. The ROHD reproducer from issue 63292 shows the same mechanism on a small pure-Dart
   package on Dart 3.13.7: no-op plugin 2.0 s versus 0.9 s native (18 s on 3.11 in the
   issue), so the issue thread's worst numbers are already gone and the remaining cost is
   exactly the per-process relink that the byte store removes.
4. Two things upstream already decided that shape the patches: `EvictingFileByteStore`'s
   own documentation says plugins must use a plain `FileByteStore` and leave eviction to
   the server (so the issue's open question has an answer in the code), and the plugin
   build folder is already keyed by SDK version plus consumer path (so keying it by
   content is a one-line change in the watcher plus a test mock).
5. The Dart and Flutter AI policies are behavioral: review and understand every line,
   verify descriptions, tests must pass; reviewers close changes with generated
   descriptions or stray files. Each branch here is small (24 to 151 lines) and comes with
   its mechanism written up, which is what makes "understand and discuss" realistic.
